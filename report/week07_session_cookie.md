### 세션과 쿠키 기반 인증 흐름 이해

> 🧩 세션과 웹 애플리케이션에서 사용자 인증 및 상태 관리를 위한 핵심적인 기술입니다. 웹은 기본적으로 무상태(Stateless) 프로토콜인 HTTP를 기반으로 작동하기 때문에, 클라이언트(브라우저)의 요청과 서버의 응답은 독립적으로 이루어집니다. 따라서 로그인 상태 유지와 같은 상태 관리가 필요할 때 세션과 쿠키가 중요한 역할을 합니다.

> 🔐**웹의 무상태성:** 웹 브라우저가 서버에 요청을 보낼 때, 서버는 해당 요청을 처리하고 응답을 보냅니다. 이때 서버는 이전 요청과 현재 요청 사이에 어떤 연관성도 가지지 않습니다. 예를 들어, 사용자가 로그인한 후 다른 페이지로 이동하면, 서버는 이 사용자가 로그인 상태인지 알 수 없습니다. 이러한 무상태성의 한계를 극복하기 위해 세션과 쿠키가 등장했습니다.

### 상태 유지 전략(Session vs Cookie)

> ✅세션과 쿠키는 모두 사용자의 "상태"를 유지하는 데 사용되지만, 데이터를 저장하는 위치와 방식에 차이가 있습니다.

1. **쿠키(Cookie) 기반 인증**

   > ✅`쿠키`는 클라이언트(브라우저) 측에 저장되는 작은 데이터 조각입니다. 서버가 웹 브라우저에 쿠키를 저장하도록 지시하면, 브라우저는 해당 쿠키를 저장하고, 이후 동일한 서버에 요청을 보낼 때마다 이 쿠키를 함께 전송합니다.

   🧩**작동흐름:** `클라이언트 로그인 요청` -> `서버 인증` -> `쿠키 생성 및 응답` -> `클라이언트 쿠키 저장` -> `이후 요청 시 쿠키 전송` -> `서버 인증 및 응답`

   - `클라이언트 로그인 요청:` 사용자가 웹사이트의 로그인 페이지에서 ID와 비밀번호를 입력하고 로그인 버튼을 클릭합니다.
   - `서버 인증:` 서버는 클라이언트로부터 받은 ID와 비밀번호를 데이터베이스에 저장된 정보와 비교하여 인증합니다.
   - `쿠키 생성 및 응답:` 인증에 성공하면, 서버는 사용자 ID, 로그인 토큰(랜덤 문자열), 만료 시간 등의 정보를 포함하는 세션 ID를 포함하지 않는 쿠키를 생성합니다. 이 쿠키는 HTTP 응답 헤더의 Set-Cookie 필드를 통해 클라이언트에게 전송됩니다.
   - `클라이언트 쿠키 저장:` 클라이언트(브라우저)는 서버로부터 받은 쿠키를 로컬에 저장합니다
   - `이후 요청 시 쿠키 전송:` 사용자가 로그인된 상태로 다른 페이지로 이동하거나, 다른 리소스에 접근할 때마다, 브라우저는 해당 도메인에 저장된 쿠키를 자동으로 HTTP 요청 헤더의 Cookie 필드에 포함하여 서버로 전송합니다.
   - `서버 인증 및 응답:` 서버는 클라이언트로부터 받은 쿠키를 검증하여 사용자가 로그인된 상태인지 확인합니다. 유효한 쿠키라면 해당 사용자의 요청을 처리하고 응답합니다.

     💡**장점:**

     - `서버 부담 감소:` 서버는 별도의 세션 저장소를 유지할 필요가 없어 서버 자원을 절약할 수 있습니다.
     - `확장성 용이:` 여러 서버에 부하 분산(Load Balancing)을 할 때 세션 동기화 문제가 발생하지 않아 확장이 용이합니다.
     - `오프라인 사용 가능성:` 만료 기간이 있는 쿠키는 브라우저를 닫았다가 다시 열어도 로그인 상태가 유지될 수 있습니다.

     ⚠️**단점:**

     - `보안 취약성:` 쿠키는 클라이언트 측에 저장되므로 XSS(Cross-Site Scripting) 공격에 취약할 수 있습니다. HttpOnly 옵션으로 JavaScript 접근을 막아 어느 정도 방어할 수 있습니다.
     - `CSRF (Cross-Site Request Forgery) 공격:` 공격자가 사용자의 브라우저를 통해 악의적인 요청을 보내는 공격에 취약합니다. SameSite 쿠키 속성, CSRF 토큰 등으로 방어해야 합니다.
     - `민감한 정보 노출 위험:` 쿠키에 사용자 정보를 직접 저장하는 것은 위험하며, 일반적으로는 세션 ID나 토큰만 저장합니다.
     - `크기 제한:` 쿠키는 하나의 도메인당 4KB 정도의 크기 제한이 있습니다.
     - `사용자 비활성화 가능성:` 사용자가 브라우저에서 쿠키를 비활성화하면 인증이 불가능합니다.

2. **세션(Session) 기반 인증**

   > ✅`세션`은 서버 측에 사용자 정보를 저장하고, 클라이언트(브라우저)에게는 해당 세션을 식별할 수 있는 세션 ID만을 부여하여 상태를 유지하는 방식입니다. 마치 사물함 열쇠를 받고 사물함에 물건을 보관하는 것과 같습니다.

   🧩**작동흐름:** `클라이언트 로그인 요청` -> `서버 인증 및 세션 생성` -> `세션 ID 쿠키 발급 및 응답` -> `클라이언트 세션 ID 쿠키 저장:` -> `이후 요청 시 세션 ID 쿠키 전송` -> `서버 세션 ID 검증 및 응답`

   💡**장점:**

   - `보안성:` 모든 민감한 사용자 정보는 서버에 저장되므로 클라이언트에 노출되지 않습니다.
   - `사용자 정보 관리 용이:` 서버에서 세션을 통해 사용자의 다양한 상태 정보를 관리할 수 있습니다.
   - `CSRF 방어 용이:` 세션 ID가 쿠키로만 전달되므로, CSRF 토큰을 활용하여 방어하기 용이합니다.

   ⚠️**단점:**

   - `서버 부담 증가:` 사용자가 많아질수록 서버는 더 많은 세션 정보를 유지해야 하므로 서버 메모리나 스토리지에 부담이 됩니다.
   - `확장성 문제 (세션 동기화):` 여러 대의 서버(로드 밸런싱 환경)를 사용할 경우, 특정 사용자의 세션 정보가 특정 서버에만 저장될 수 있습니다. 다른 서버로 요청이 가면 세션 정보를 찾을 수 없어 인증 오류가 발생합니다. 이를 해결하기 위해 세션 클러스터링, 세션 스티키(Sticky Session), 중앙 집중식 세션 저장소(Redis, 데이터베이스 등)를 사용해야 합니다.
   - `싱글 사인 온(SSO) 구현 어려움:` 여러 도메인 간에 로그인 상태를 공유하기 어렵습니다.
   - `클라이언트 비활성화 가능성:` 사용자가 브라우저에서 쿠키를 비활성화하면 세션 ID를 전달할 수 없어 인증이 불가능합니다.

### 로그인 구조 적용 예시

> 🔐 실제 웹 서비스에서는 세션과 쿠키를 단독으로 사용하기보다는 상황에 맞게 조합하거나, 최신 트렌드인 토큰 기반 인증(JWT)을 활용하기도 합니다.

1. 전통적인 웹 서비스 (Session 기반)

   > ✅ 대부분의 기존 웹 애플리케이션 (예: JSP, PHP, ASP.NET 기반)은 세션 기반 인증을 기본으로 사용합니다.

   `로그인 시나리오:`

   - I. 사용자가 ID/PW 입력 -> 서버 전송
   - II. 서버 인증 후, 사용자 정보를 DB에서 가져와 세션 저장소(메모리 또는 Redis 등)에 저장하고 세션 ID 생성
   - III. 생성된 세션 ID를 JSESSIONID와 같은 이름의 쿠키로 클라이언트에 발급
   - IV. 클라이언트는 이후 요청마다 이 세션 ID 쿠키를 전송
   - V. 서버는 세션 ID로 세션 저장소에서 사용자 정보 조회 후 요청 처리

   > 🧩 **사용예시:** 온라인 쇼핑몰, 커뮤니티 사이트 등 사용자 활동이 많고 서버에서 사용자 상태를 적극적으로 관리해야 하는 경우.

2. REST API 서비스 (토큰 기반 - JWT)

   > ✅ 최근에는 세션/쿠키의 단점을 보완하고 모바일 앱, SPA(Single Page Application) 등 다양한 클라이언트 환경에 유연하게 대응하기 위해 **토큰 기반 인증(JWT: JSON Web Token)** 방식이 널리 사용됩니다. JWT는 비대칭 암호화와 해싱을 활용하여 인증 정보를 자체적으로 담고 있습니다. JWT는 기본적으로 무상태(Stateless)입니다. 서버가 클라이언트의 상태를 직접 저장하지 않고, 토큰 자체에 필요한 모든 정보가 담겨있으므로 서버의 확장성이 매우 뛰어납니다. 하지만 토큰 탈취에 대한 보안, 토큰 만료 관리 등의 추가적인 고려가 필요합니다.

   `로그인 시나리오:`

   - I. 사용자가 ID/PW 입력 -> 서버 전송
   - II. 서버 인증 후, 사용자 정보를 DB에서 가져와 JWT 토큰 생성
   - III. 서버는 생성된 JWT를 HTTP 응답의 body에 담아 클라이언트에 전송 (쿠키가 아님)
   - IV. 클라이언트 (브라우저의 로컬 스토리지, 세션 스토리지 또는 쿠키에 JWT 저장)는 이후 요청마다 HTTP 요청 헤더의 Authorization 필드에 JWT를 담아 서버로 전송
   - V. 서버는 JWT의 유효성을 검증(서명 확인, 만료 시간 확인 등). 유효한 토큰이면 해당 사용자의 요청 처리

   > 🧩 **사용예시:** React, Vue, Angular 기반의 SPA, 모바일 앱 백엔드 API, 마이크로서비스 아키텍처 등.

3. 하이브리드 접근

   > ✅ 실제로는 세션과 쿠키를 함께 사용하거나, JWT와 쿠키를 조합하는 방식도 많습니다.

   `예를 들어:`

   - I. `JWT를 쿠키에 저장:` JWT는 본질적으로 토큰이지만, XSS 공격으로부터 보호하기 위해 HttpOnly 쿠키에 저장하여 사용하는 경우가 있습니다.
   - II. `단기 세션과 장기 쿠키:` 세션은 짧은 시간 동안만 유효하게 하고, "로그인 유지" 기능처럼 오랜 시간 로그인 상태를 유지해야 할 때는 만료 기간이 긴 쿠키를 사용하여 자동 로그인 기능을 구현하기도 합니다.
